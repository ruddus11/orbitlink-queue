# OrbitLink 기술 개발 전체 목록

**기준:** 2026-11-05에 지정된 소스와 실행 기록을 읽고 정리한 계획. 경연 한 사람이 남은 기술 개발과 통합을 맡는 경우를 기준으로 한다. 이 문서는 작업 목록이며, 아래의 새 파일과 함수 이름은 **제안**이다.

**수치 구분:** 큐 용량, 실험 결과, 데모 설정값은 기존 파일에 있는 값만 인용했다. 아래 **예상 소요 시간은 실측값이 아닌 일정 편성을 위한 추정치**다. 실제 구현 결과나 성능 목표치로 읽지 않는다. 시간은 순수 개발·검증 작업 시간이며 발표 연습과 팀 의사결정 대기 시간은 제외한다.

## 1. 지금 상태 한눈에 보기

|---|---|---|

| XOR 전송 데이터 보호 | ⬜ 미구현 | 메시지의 `encrypted` 표시만 있다. 암호화·복호화 함수와 호출 경로는 없다. XOR은 과제용 시뮬레이션이며 무결성·실제 보안을 보장하지 않는다. |

| 통합 앱·재현 가능한 검증·최종 데모 | ⬜ 미구현 | `main_demo.c`는 큐 모듈 단독 실험용이다. 최종 `main`과 통합 테스트·발표용 실행 절차가 필요하다. |

**현재 측정 기준선:** `결과/시나리오_결과.txt`에서 자가 검사 실패 0건, 시나리오 2의 Normal 실패 콜백 318회·재전송 성공 16회·Retry 대기함 넘침 267건이다. **318은 고유 메시지 수가 아니라 콜백 호출 수**이며 재시도 실패도 다시 콜백을 부른다. 비교 실험의 Emergency 평균 대기는 단일 FIFO 644.0 tick, Sender 우선순위만 올린 FIFO 644.0 tick, 우선순위 큐 10.0 tick이었다. 이 값들은 현 데모의 결과로만 인용하고 최종 앱의 예상 성능으로 사용하지 않는다.

### 구현 때 지킬 경계

- `msg_queue.c`는 이미 완성된 큐 모듈로 취급한다. 최종 앱은 공개 `mq_*` API를 사용하고 데모용 태스크 코드를 그대로 제품 코드로 간주하지 않는다.
- 메시지 **처리 우선순위**는 큐의 수신 순서이고, FreeRTOS **태스크 우선순위**는 CPU 배분이다. 비교 실험은 Sender 태스크 우선순위만 높여도 FIFO 수신 순서가 바뀌지 않음을 보여 준다.
- `timestamp`는 최초 생성 tick이고 `enqueue_tick`은 각 `mq_send()`에서 복사본에 기록된다. 재시도별 큐 대기와 전체 수명 시간을 같은 값으로 혼동하지 않는다.
- `payload`는 문자열이 아니다. 암호화 후 `0x00`이 생길 수 있으므로 항상 `payload_len`을 사용한다. XOR을 두 번 적용하면 평문이 되므로 Retry는 변환 함수를 호출하지 않는다.
- 기존 POSIX 시뮬레이터는 태스크 안의 직접 `printf`를 경계한다. Logger의 출력 경로는 데모 `vLog()`의 크리티컬 섹션 처리를 참고하되, 긴 출력이 스케줄링에 주는 영향도 측정한다.
- 최종 결과는 **tick 기준**으로 비교한다. 기존 README에 POSIX 포트의 실제 경과 시간이 tick과 정확히 같지 않다고 적혀 있다.

## 3. 개발 순서와 발표 일정

**의존성 순서:** ① 계약·설정 → ② XOR 및 ⑥ Logger 사건 API → ③ Sender·④ Receiver → ⑤ Retry → ⑦ 통합 앱 → ⑧ 통합 시험 → ⑨ 측정·데모 → ⑩ 문서. Logger API의 최소 형태는 Sender/Receiver 작성 전에 고정하고, Logger 태스크 내부 구현은 병행할 수 있다.

## 4. 팀 결정이 필요한 항목

| 결정 | 정해야 할 내용과 권장 출발점 | 결정이 늦으면 생기는 영향 |
|---|---|---|
| XOR 키 관리·적용 범위 | 고정 키를 설정 파일/헤더에서 공유할지, 실행 인자로 줄지 정한다. 과제 시뮬레이션이므로 **payload만** 변환하고 `type`, `id`, 길이는 그대로 두는 구조도 제안을 출발점으로 삼는다. 키 값과 변경 규칙은 팀이 정한다. | Sender·Receiver·테스트의 인터페이스가 갈린다. 다른 키를 쓸 때는 복호화 결과가 달라져도 XOR 자체에는 오류 검출 기능이 없다. |
| Retry 횟수·backoff·대기함 | 데모의 최대 3회, 50/100/200 tick과 구조도 설명의 **제안** 10/20/40 tick 중 운영 기준을 정한다. 대기함 크기, 유형별 우선권, 가득 찼을 때 버림/대체, 만료와 종료 시 잔여 메시지 정책을 함께 정한다. | 대기함 자료구조·통계·시나리오 기대 결과가 달라진다. 기존 16칸 대기함은 시나리오 2에서 267건 넘쳤으므로 크기만 늘리는 것으로 개선을 가정하지 않는다. |
| Logger와 Monitor 관계 | Logger가 `mq_get_status()`를 주기적으로 호출해 Monitor를 흡수할지, Monitor가 스냅샷을 Logger에 전달할지 정한다. **권장 출발점:** 관찰과 출력을 Logger에 모아 한 출력 경로만 둔다. 주기와 로그 큐 포화 정책도 결정한다. | 태스크 수·우선순위·로그 형식·메모리 사용이 달라진다. `mq_get_status()`만으로 메시지별 구조화 로그를 만들 수는 없다. |
| 태스크 우선순위·처리 시간 | 데모의 Sender 3, Receiver 2, Retry 2, Monitor 5는 실험 설정이다. 최종 앱의 우선순위, 처리 시간 흉내를 유지할지, 긴급 Sender의 별도 우선순위를 줄지 정하고 과부하에서 기아를 확인한다. | 최종 측정값과 설명이 달라진다. 메시지 수신 우선순위와 태스크 스케줄링 설명을 섞기 쉽다. |
| 로그 보관·발표 측정 기준 | 콘솔만 쓸지 파일도 남길지, CSV 스키마와 실행 시드·조건을 어떻게 기록할지 정한다. 통계의 `failed`는 전송 시도 실패 횟수이며 고유 메시지 유실 건수와 다르다는 기준을 합의한다. | 중간·최종 발표 수치를 재현하거나 서로 비교하기 어렵다. |

## 5. 파트 분배 후보

**경연이 끝까지 쥘 핵심:** 공용 API와 설정 확정, Retry 실패·종료 정책, 최종 `main` 통합, 전체 정합성·우선순위 검증. 이 부분들은 모듈 사이 책임 경계가 많아 한 사람이 최종 결정을 해야 한다.

**떼어주기 좋은 독립 작업:** XOR 변환과 왕복 검사, 결과 요약 스크립트, 실행 안내·발표 자료 정리. Logger는 사건 API를 경연이 먼저 고정한 뒤 내부 구현과 출력 형식을 분리해 맡길 수 있다. Sender·Receiver는 같은 메시지 계약을 공유하므로 단독 담당자에게 넘기더라도 통합 검증은 경연이 맡는다.
